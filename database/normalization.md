# Normalization

## 한 줄 정의

정규화는 데이터 중복을 줄이고 데이터 일관성을 지키기 위해 테이블을 적절히 나누는 과정입니다.

## 왜 필요한가

중복 데이터가 많으면 수정할 때 일부만 바뀌어 데이터가 서로 맞지 않는 문제가 생길 수 있습니다.

예를 들어 질문마다 카테고리 설명을 문자열로 반복 저장한다고 생각해봅니다.

```text
질문1: category=JAVA, categoryDescription=자바 언어
질문2: category=JAVA, categoryDescription=자바 언어
질문3: category=JAVA, categoryDescription=Java language
```

같은 카테고리인데 설명이 다르게 저장될 수 있습니다.

## 핵심 개념

- 1정규형: 컬럼 하나에는 원자적인 값 하나만 둡니다.
- 2정규형: 복합키 일부에만 의존하는 컬럼을 분리합니다.
- 3정규형: 기본키가 아닌 컬럼에 의존하는 컬럼을 분리합니다.

처음부터 모든 정규형을 외우기보다 아래 감각을 먼저 잡는 것이 좋습니다.

```text
중복이 반복된다
-> 별도 테이블로 뺄 수 있는가?

한 값이 바뀌면 여러 행을 같이 수정해야 한다
-> 정규화 후보
```

## 내 프로젝트와 연결

`backend-interview-tracker`의 `Question` 엔티티는 현재 아래 필드를 가집니다.

```text
id
title
answer
source
category
status
createdAt
updatedAt
```

현재 `category`와 `status`는 enum입니다.

```java
@Enumerated(EnumType.STRING)
private Category category;
```

카테고리 종류가 고정되어 있고 설명이나 권한 같은 추가 정보가 없다면 enum으로 관리해도 단순합니다.

하지만 나중에 카테고리별 설명, 표시 순서, 색상, 사용자별 커스텀 카테고리가 필요해지면 `Category`를 별도 테이블로 분리하는 것이 좋아질 수 있습니다.

```text
questions
  id
  title
  answer
  category_id

categories
  id
  name
  description
  display_order
```

## 정규화와 반정규화

정규화는 중복을 줄여 일관성을 높입니다. 하지만 조회할 때 JOIN이 많아져 복잡해질 수 있습니다.

반정규화는 조회 성능이나 단순성을 위해 일부 중복을 허용하는 방식입니다.

```text
정규화
-> 데이터 일관성에 유리
-> JOIN 증가 가능

반정규화
-> 조회 단순화 가능
-> 중복과 불일치 위험 증가
```

## 30초 면접 답변

정규화는 데이터 중복을 줄이고 일관성을 지키기 위해 테이블을 적절히 나누는 과정입니다. 같은 데이터가 여러 곳에 반복되면 수정 시 일부만 바뀌어 불일치가 생길 수 있습니다. 제 `backend-interview-tracker`에서는 현재 카테고리와 상태가 고정된 enum이라 단순하게 관리하지만, 카테고리 설명이나 사용자별 커스텀 카테고리가 필요해지면 별도 테이블로 분리하는 정규화를 고려할 수 있습니다.

## 꼬리질문 대비

### 정규화는 항상 좋은가요?

항상 좋은 것은 아닙니다. 데이터 일관성에는 좋지만 조회가 복잡해지거나 JOIN이 많아질 수 있습니다. 그래서 읽기 성능이 중요한 경우에는 반정규화를 일부 적용하기도 합니다.

### enum과 테이블 중 무엇이 좋나요?

값이 고정되어 있고 추가 정보가 필요 없다면 enum이 단순합니다. 값이 자주 바뀌거나 관리 화면이 필요하거나 설명/순서/권한 같은 메타데이터가 생기면 테이블로 분리하는 편이 좋습니다.
